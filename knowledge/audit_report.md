# Audit Report: SSE and Socket.io Usage

**Date**: 2026-01-13
**Auditor**: Antigravity

## Executive Summary
The application currently uses both Server-Sent Events (SSE) and Socket.io.
- **SSE** is used effectively for business notifications (tickets, approvals).
- **Socket.io** contains a **critical performance anti-pattern**: broadcasting all server console logs to all connected clients.

## Findings

### 1. Critical Performance Risk: Socket.io Log Broadcasting
- **File**: `index.js` (Lines 172-182)
- **Code**:
  ```javascript
  console.log = function (...args) {
    // ...
    io.emit("new_log", msg); // <--- BROADCAST TO ALL
  };
  ```
- **Impact**: With 1000 users, every single server log (DB query, request info, error) generates 1000 network messages. This is O(N*M) complexity where N=Users and M=LogFrequency. This acts as a self-inflicted DDoS attack under load.
- **Recommendation**: **REMOVE THIS IMMEDIATELY** or restrict it to a specific room (`io.to('admin_debug_room').emit(...)`) that only developers join.

### 2. Scalability of Connection Management
- **SSE**: Stores connections in local memory (`core/sse-manager.js`).
  - **Limitation**: If the server is scaled horizontally (e.g., using PM2 cluster mode or Kubernetes), users connected to Instance 1 will not receive notifications generated by actions on Instance 2.
- **Recommendation**: Implement Redis Pub/Sub to synchronize events across server instances.

### 3. Connection Limits
- **Observation**: `routers/sse.js` sets `res.setTimeout(0)` (correct).
- **Risk**: Linux servers default to 1024 open files. 1000 users + DB connections + static files > 1024.
- **Recommendation**: Increase `ulimit -n` to at least 65535 in the production environment setup.

### 4. Code Quality
- **SSE Manager**: The `broadcast` loop is synchronous.
  - Risk: Large loops block the Node.js event loop.
  - Fix: Use `setImmediate` or chunk the broadcast to avoid blocking the main thread if users > 5000.

## Action Plan (Proposed)

1.  **Refactor Socket Logger**: Change global emit to targeted emit (room-based).
2.  **Stress Test**: Run a script opening 1000 dummy connections to verify stability.
3.  **Documentation**: Add "Scaling" section to developer guide mentioning Redis requirement for future growth.

## Conclusion
For the use case "thousands of people opening tab together", the current **Socket.io log broadcast is a show-stopper**. It will cause severe lag. SSE is implemented correctly for its purpose but needs architectural changes (Redis) if the backend infrastructure scales beyond a single node.
